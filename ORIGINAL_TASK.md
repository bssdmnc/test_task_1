# Оригинальная задача (выжимка)

Общее описание методологии: как из реального pull request'а сделать оценочную задачу для кодящего ИИ-агента. Конкретику по нашему PR см. в [README.md](README.md).

## Цель

Превратить реальный pull request в оценочную задачу для кодящего агента. Каждая задача должна:

- включать состояние репозитория **непосредственно перед** вливанием изменения;
- определять детерминированное окружение выполнения (Docker);
- включать качественную постановку задачи (problem statement);
- включать тесты, проверяющие исправление.

Во время оценки агент получает **только** постановку задачи + базовый репозиторий и реализует решение **самостоятельно**.

## Из чего состоит задача

1. **Состояние базового репозитория** — репозиторий, зафиксированный на коммите непосредственно перед вливанием исходного PR. Изменение, задуманное в исходном PR, доступно отдельно как «existing solution».
2. **Золотое решение (Golden Solution)** — чистая, независимая повторная реализация исправления; не копирует исходный PR дословно; по качеству — не ниже оригинала.
3. **Окружение выполнения** — на основе Docker (каталог `.agen-runtime/`); обеспечивает воспроизводимость сборки и прогона тестов.
4. **Разбиение тестов:**
   - **Fail-to-Pass (F2P)** — проверяют баг/недостающую функциональность; падают на базовом коммите; проходят после золотого решения.
   - **Pass-to-Pass (P2P)** — существующие тесты, не затронутые правкой; проходят и до, и после (защита от регрессий).
5. **Постановка задачи (промпт для LLM)** — структурированное, самодостаточное описание проблемы; единственный вход агента при оценке.
6. **Файл метаданных** — `.agen-runtime/metadata.json`: постановка задачи, подсказки (hints), сопоставления тестов.

## Процесс

### Окружение
Каталог `.agen-runtime/` содержит три ключевых файла:
- `Dockerfile.agen-runtime` — базовый образ под язык репозитория с управлением зависимостями;
- `run-tests-eval.sh` — скрипт сборки образа и запуска тестов;
- `metadata.json` — метаданные задачи.

> Если выдан подготовительный PR настройки Docker — сначала проверьте, одобрите и влейте его, и только потом начинайте работу.

### Разработка решения

Создайте ветку решения от ветки по умолчанию:

```bash
git checkout <default-branch>   # main / master / dev
git pull
git checkout -b golden-solution
```

Внесите существующее решение, чтобы видеть полный diff оригинала:

```bash
git checkout existing-solution -- .
```

Улучшите решение, взяв оригинал за основу:
- сохраните корректную логику и работающие части;
- улучшите читаемость и структуру;
- рефакторите там, где уместно;
- надёжнее обрабатывайте граничные случаи.

Первый коммит — **только реализация**, без тестов (удалите изменения тестов из патча):

```bash
git commit -am "[sol]: feature code"
```

### Политика исправления Docker
Если Docker сломан: правьте в отдельной ветке `docker-golden-solution`, сначала влейте её в `main`, затем сделайте rebase ветки `golden-solution` на обновлённый `main`.

### Валидация
- Docker собирается успешно, тесты исполняются внутри контейнера.
- **F2P:** падают до `[sol]` → проходят после `[sol]`.
- **P2P:** проходят и до, и после.

## Структура коммитов

Вся работа — в ветке `golden-solution`, строго в этом порядке и с обязательными префиксами на каждом коммите:

```
[sol]:  feature code        # изолированный код решения (без тестов и лишних изменений)
[f2p]:  fail to pass tests   # тесты, падающие на базовом коммите
[meta]: metadata.json        # постановка задачи, варианты, пути к тестам, подсказки
```

## Требования к Pull Request

**Заголовок:** `[GOLDEN SOLUTION] <заголовок исходного PR>`

**Описание должно включать:**
1. **Проблема** — что было сломано/отсутствовало.
2. **Подход** — как работает ваше решение и чем оно лучше исходного PR.
3. **Стратегия тестирования** — какое поведение проверяется и какие граничные случаи покрыты.

## Критерии приёмки

Задача будет отклонена, если выполнится **любое** из:
- Docker не собирается или не запускает тесты;
- F2P-тесты не дают строгий переход «падение → прохождение»;
- P2P-тесты падают в какой-либо момент;
- постановка задачи расплывчата или неполна;
- золотое решение не является корректным/полным решением постановки;
- структура/префиксы коммитов некорректны;
- тесты нестабильны (flaky) или недетерминированы.

## Модель оценки

Агент получает: базовый репозиторий (сломанное состояние) и **только** `problem_statement`.
Агент **не видит**: ваше решение, ваши тесты, исходный PR.

Качество задачи оценивается по тому, способен ли агент: реализовать исправление, пройти все F2P-тесты, сохранить все P2P-тесты.

## Ключевой принцип

> Вы не исправляете баг. Вы проектируете качественную оценочную задачу, которая проверяет, способен ли ИИ исправить этот баг.

## Схема поставки (CSV)

Данные сдаются в виде CSV. Минимальный набор столбцов:

| Столбец | Пояснение |
| --- | --- |
| `repo_url` | Полный URL предоставленного репозитория |
| `repo` | Полное имя репозитория |
| `instance_id` | Идентификатор задачи (как правило, совпадает с `repo`) |
| `base_commit` | Полный 32-символьный SHA последнего коммита в ветке по умолчанию |
| `test_commit` | Полный 32-символьный SHA коммита `[f2p]` (тесты fail-to-pass) |
| `pass_to_pass` | Пути к файлам P2P-тестов через запятую (от корня репозитория) |
| `fail_to_pass` | Пути к файлам F2P-тестов через запятую (от корня репозитория) |
| `problem_statement` | Содержимое промпта для LLM |
| `problem_statement_variant` | Более сложная версия промпта (как его дал бы нетехнический человек) |
| `golden_commit` | Полный 32-символьный SHA коммита `[sol]` (код решения) |

**Пример** (значения-плейсхолдеры):

```csv
repo_url,repo,instance_id,base_commit,test_commit,pass_to_pass,fail_to_pass,problem_statement,golden_commit
<repo_url>,<repo>,<instance_id>,<base_commit_sha>,<test_commit_sha>,"<p2p_path_1>,<p2p_path_2>","<f2p_path_1>,<f2p_path_2>","<текст промпта>",<golden_commit_sha>
```

> Расширенный формат итоговой строки датасета (полный набор столбцов, содержимое Dockerfile/скрипта и т. п.) описан в [README.md](README.md), раздел «metadata.csv».
